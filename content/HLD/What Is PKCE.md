## 1. What Is PKCE?

PKCE stands for **Proof Key for Code Exchange**. It is an extension to the OAuth 2.0 Authorization Code Flow that protects against authorization code interception.

It was originally designed for public clients such as mobile applications, which cannot securely store a client secret.

PKCE is now also commonly used by Single Page Applications (SPAs), such as React applications.

### The Problem PKCE Solves

In OAuth 2.0 Authorization Code Flow, the application receives an authorization code after the user authenticates.

An attacker who intercepts this authorization code may attempt to exchange it for an access token.

PKCE prevents the intercepted code from being useful without an additional secret known only to the legitimate client.

## 2. How Does PKCE Work?

PKCE uses two values:

| Value            | Description                                               |
| ---------------- | --------------------------------------------------------- |
| `code_verifier`  | A cryptographically random secret generated by the client |
| `code_challenge` | A derived value sent to the authorization server          |

The client generates a `code_verifier` and computes the `code_challenge` using SHA-256.

    code_challenge =
        BASE64URL(SHA256(code_verifier))

The verifier remains with the client. The challenge is sent to the authorization server during the authorization request.

### PKCE Flow

1. The user opens the application.
2. The application generates a random `code_verifier`.
3. It calculates the `code_challenge` using SHA-256.
4. The application redirects the user to the authorization server with the challenge.
5. The user authenticates and grants the requested authorization.
6. The authorization server redirects back with an authorization code.
7. The client sends the authorization code and original `code_verifier` to the token endpoint.
8. The authorization server calculates the challenge from the verifier and compares it with the original challenge.
9. If they match, the authorization server issues the tokens.

If an attacker intercepts the authorization code but does not have the verifier, they cannot successfully exchange the code for a token.

**Important:** Use the `S256` challenge method. The older `plain` method does not provide the same protection.

## 3. Where Is PKCE Used?

PKCE is commonly used with OAuth 2.0 Authorization Code Flow in:

- Mobile applications.
- React, Angular, and other browser-based SPAs.
- Native desktop applications.
- Public clients that cannot safely keep a client secret.

PKCE is also recommended for confidential clients, such as server-side web applications, when using the Authorization Code Flow.

## 4. Can PKCE Protect a Public-Facing Website?

**Yes, but it protects a specific part of the authentication flow.**

Suppose you have a public-facing React website that accesses protected backend APIs.

A typical architecture could look like this:

    User's Browser
          |
          v
    React Website
          |
          | OAuth 2.0 Authorization Code Flow + PKCE
          v
    Identity Provider
    (Keycloak, Okta, Microsoft Entra ID, etc.)
          |
          | Access Token
          v
    React Website
          |
          | HTTPS + Access Token
          v
    Spring Boot REST API
          |
          v
    Database

### How This Works

1. The user opens the public website.
2. The React application redirects the user to an identity provider.
3. The user signs in.
4. The identity provider returns an authorization code.
5. The React application exchanges the code using PKCE.
6. The application obtains an access token.
7. The React application sends the access token when calling the Spring Boot API.
8. Spring Security validates the token and checks the user's permissions.

PKCE protects the authorization code exchange from interception.

The Spring Boot API must still validate the access token and enforce authorization rules.

## 5. What PKCE Does NOT Protect

PKCE is not a complete website security solution.

| Threat                              | Does PKCE protect against it?                 |
| ----------------------------------- | --------------------------------------------- |
| Authorization code interception     | Yes, when correctly implemented               |
| Unauthorized access to backend APIs | No, APIs must validate tokens and permissions |
| Cross-Site Scripting (XSS)          | No                                            |
| SQL Injection                       | No                                            |
| Cross-Site Request Forgery (CSRF)   | No, not by itself                             |
| Stolen access token                 | No                                            |
| DDoS attacks                        | No                                            |

For example, if an attacker injects JavaScript into a React application and steals an access token, PKCE does not prevent the attacker from using that token.

## 6. How Would You Secure a Public-Facing Website?

There are two common approaches.

### Option A: SPA + PKCE

For a React SPA:

- Use OAuth 2.0 Authorization Code Flow with PKCE.
- Use an established identity provider.
- Validate access tokens at the backend.
- Enforce roles and permissions using Spring Security.
- Use HTTPS everywhere.
- Protect against XSS.
- Avoid storing long-lived sensitive tokens in browser-accessible storage when possible.

This approach is common for SPAs, but browser token handling requires careful security design.

### Option B: Backend-for-Frontend (BFF)

A BFF is often a stronger choice for applications where sensitive data is involved.

    Browser
       |
       | Secure Session Cookie
       v
    Spring Boot BFF
       |
       | OAuth Tokens stored server-side
       v
    Identity Provider / APIs

In this design:

- The browser uses a secure session cookie.
- The backend handles OAuth authorization and token exchange.
- Access and refresh tokens are stored server-side.
- The browser does not directly handle OAuth access tokens.
- The backend proxies requests to protected APIs.

The cookie should be configured with appropriate `HttpOnly`, `Secure`, and `SameSite` attributes. CSRF protection is also important for cookie-based authentication.

A BFF reduces the risk of token theft through browser JavaScript, although it does not eliminate XSS or CSRF risks entirely.

## 7. PKCE vs Client Secret

| PKCE                                              | Client Secret                     |
| ------------------------------------------------- | --------------------------------- |
| Uses a per-request verifier                       | Uses a client credential          |
| Designed for public clients                       | Designed for confidential clients |
| Verifier is temporary                             | Secret is long-lived              |
| Cannot be embedded as a permanent secret in a SPA | Must remain on a trusted server   |
| Protects authorization code exchange              | Authenticates the client          |

A React application is a public client. Any secret embedded in its JavaScript bundle can be extracted by users, so it should not rely on a client secret.

## 8. Interview Answer

"PKCE stands for Proof Key for Code Exchange. It is an OAuth 2.0 extension that protects the Authorization Code Flow from authorization code interception.

The client generates a random code verifier and derives a code challenge from it using SHA-256. The challenge is sent during the authorization request, and the verifier is sent when exchanging the authorization code for tokens. The authorization server validates the relationship between them before issuing tokens.

PKCE is commonly used in mobile applications and browser-based SPAs such as React applications.

For a public-facing website, PKCE helps secure the login flow, but it does not secure the complete application. The backend APIs must still validate access tokens and enforce authorization. For sensitive applications, a Backend-for-Frontend architecture can keep OAuth tokens on the server and use a secure session cookie in the browser."
